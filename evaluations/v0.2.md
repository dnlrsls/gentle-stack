# v0.2 evaluation record

This is an author-directed exercise on Windows with Python and Git, plus a local Engram read/write check. It is not an independent agent evaluation, a cross-provider benchmark, or a live tracker/delivery test. The v0.2 label identifies this iteration; no packaged release or tag is implied.

## 1. Refactor into work units

Request: refactor duplicated payment fee calculations without changing public functions or results; prepare tickets but do not publish them.

Fixture baseline:

```python
def checkout(cents):
    return cents + (cents * 3 + 99) // 100

def refund_fee(cents):
    return (cents * 3 + 99) // 100
```

Draft A: **Extract shared fee calculation and migrate checkout**.

- Outcome: a shared integer-arithmetic fee helper used by checkout.
- Scope: the helper, checkout, and their regression coverage. Exclude refund migration and public API changes.
- Acceptance: checkout returns 0, 2, 103, 105, and 10300 for inputs 0, 1, 100, 101, and 10000 respectively. Refund behavior remains unchanged. Existing names and signatures remain available.
- Verification: run checkout and refund regression tests against these explicit baseline expectations.
- Dependencies: none.
- Completion: implemented and verified; integration must be confirmed before closure under a merge-based policy.

Draft B: **Migrate refund_fee to the shared helper**.

- Outcome: refund_fee delegates fee arithmetic to the same helper.
- Scope: refund implementation and regression coverage; no fee-rate or rounding changes.
- Acceptance: refund_fee returns 0, 1, 3, 4, and 300 for the same five inputs; checkout remains unchanged and there is one shared calculation.
- Verification: run both public-function regressions and inspect remaining arithmetic duplication.
- Dependencies: Draft A provides the helper; these units are sequential, not parallel writers.
- Completion: implemented, verified, and integrated under the project's existing completion policy.

Observed: the breakdown keeps tests with each behavior and exposes the dependency without creating product task folders. These are drafts; external issue publication, deduplication, and dependency API updates remain untested.

## 2. Implement, verify, and self-review one unit

A disposable Git repository outside Gentle Stack contained the baseline, a test file, and an ignore rule for Python bytecode. Draft A was applied by introducing `fees.py` and changing checkout to call its helper; refund_fee was left for Draft B.

Observed results:

- Baseline: two tests passed, containing ten explicit boundary assertions in total.
- Draft A: the same two tests passed; candidate identity was equal before and after execution.
- Self-review inspected the extraction against the public API and integer-rounding constraints. No issue was found in that limited extraction; there was no independent reviewer.
- A subsequent intentional rate change from 3 to 4 changed the identity of the untracked helper and failed checkout verification (`104 != 103`). Refund verification continued to pass. The previous receipt and successful checkout evidence were therefore historical.

An initial rapid same-size edit reused Python bytecode and misleadingly passed. Repeating checks with fresh external bytecode-cache locations and disabled bytecode writes exposed the regression. The verify skill now explicitly considers execution caches and installed code. This demonstrates a limit of source identity: execution environment also matters.

No commit, PR, ticket closure, or deployment was performed in this fixture. Draft B remains pending. The expected next action is to correct the regression, rerun affected checks, and reassess the changed review surface before continuing.
